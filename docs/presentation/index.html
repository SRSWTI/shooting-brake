Shooting Brake

one model, one forward pass,
split across two vendors' GPUs.

Nobody ships this. Frameworks split work between machines, or run a whole model on one vendor's cards. Shooting Brake splits a single model down the middle inside every single token: NVIDIA silicon does the thinking, two Intel cards hold and compute the knowledge, and a hand built handshake stitches them into one forward pass, 47 times per token.

Act I  ·  what it is and how it got here

what cross vendor inference means

A large language model is a stack of layers. Every token you read was pushed through all of them, one after another. Normally that stack lives on one GPU, or on several GPUs from the same vendor talking over a fast private link like NVLink.

We do something different. In this machine the stack is cut horizontally inside each layer. The attention math and the router run on an RTX 5090. The expert weights, which are the bulk of the model, sit on two Intel Arc Pro B70 cards. Both halves have to meet in the middle for every single layer of every single token.

That is harder than it sounds, and the reason is boring and brutal: CUDA and Intel's runtime share nothing. No common stream, no common event, no shared synchronisation primitive, no way for one to wait on the other. They are two separate worlds that happen to be plugged into the same motherboard. Everything in this document exists because we had to build a bridge between those worlds and then make it fast.

the intuition

Think of a chef and two enormous pantries in another room. The chef knows the recipe and does all the technique. The pantries hold the ingredients, far too many to keep on the counter. For every step of every dish, the chef has to ask the pantries for exactly the right ten ingredients out of two hundred and eighteen, and wait. The trick is not making the pantries faster. The trick is the asking.

how we got here

This went through four distinct shapes before it looked like an engine, and each shape answered one question the previous one could not.

the first version was a hand written inference server

Before any of this was about two vendors, it was a local inference server written from scratch in C++17: its own kernels, its own speculative prefill and decode, and a stated principle that every optimisation targets one specific model family on one specific piece of hardware rather than trying to be general. That codebase is sitting in the first commit. It is not what runs today, and it was never meant to be. What it gave us was the instinct that the interesting wins live at the kernel and scheduling level, not in the framework above them.

then a prototype, to test whether cross vendor worked at all

The question was not "is this fast". It was "can two vendors' GPUs cooperate inside one model at all". So the next shape was a deliberately crude cross-vendor provider: a single SYCL translation unit that took routed expert work from the CUDA side, ran it on the Intel card, and handed results back. It ran a Qwen 35B class model at 15 to 19 tokens per second with no custom kernels and no optimisation whatsoever. That figure predates our instruments, so treat it as an honest memory of the floor, not a benchmark.

Crude as it was, it settled four things that everything since depends on:

  • the transport works. A fixed ring of pinned host buffers can carry routed expert requests from CUDA to Intel and back, without either runtime knowing about the other.
  • the numbers come out right. It converted signed 4-bit group-64 quantised weights into the layout the Intel kernel wanted, and produced correct output. Correctness across a vendor boundary was no longer a hypothesis.
  • placement is expressible. You can decide which experts live on which device and have both sides agree, consistently, at runtime.
  • failure has defined behaviour. When the remote side fails, the system knows what to do rather than hanging or producing garbage.

And it settled one negative, which mattered just as much: this thing must not host production models. It proved the lifecycle, it was never going to carry real serving.

choosing which parts to keep

At that point there were three existing codebases that each did part of the job, and the central decision was which part to take from each. Getting this wrong would have cost months.

candidatewhat we tookwhat we refused, and why

So: vLLM owns the model, we own the boundary, Intel owned the math. That last part changed later, and the fact that only one third of it changed is the point of drawing the boundary carefully.

the rules we set before writing code

The plan committed on day one included constraints that read like paranoia and turned out to be exactly right. Every one of them was written because the prototype had shown us the failure it prevents.

  • a fixed ring, allocated once. Never allocate on the hot path. Allocation means the driver, and the driver means unpredictable pauses in the middle of a token.
  • never pull a value back to the CPU mid-layer, and never synchronise the whole device. Both are the easy way to write this, and both destroy the overlap between the two vendors' work. The cost of a single careless "read this number" is the entire parallelism you were trying to buy.
  • batching is mandatory, not an optimisation. One expert weight read has to serve many tokens or the memory traffic makes the whole idea pointless.
  • decode and prefill get different dispatch policies. Written before we could measure why. It is now the single most important fact about this system.
  • every model needs an explicit capability manifest and its own correctness gate. Unsupported models stay on plain vLLM rather than silently entering an unvalidated path.

eight phases of implementation

Each phase existed to kill one specific risk, and each ended in a gate that either passed with numbers or blocked the next phase.

phasethe risk it killed
0. freeze the compatibility contract Pin exactly which upstream versions and model shapes we claim to support, so "it broke" can never be ambiguous.
1. a persistent provider The Intel side must be a long lived process holding its weights resident. Loading per request would dominate everything.
2. a versioned cross process ring Two processes sharing pinned memory need a layout contract with a version number, or a mismatched build corrupts silently instead of failing.
3. qualify the provider's mathematics alone Prove the expert math is right outside the model, against a reference. If you only test end to end you cannot tell a kernel bug from a plumbing bug.
4. the vLLM plugin with hybrid MoE Insert into vLLM's routed expert lifecycle without forking vLLM.
5. compact expert ownership placement Both sides must agree on who owns which expert, with the ids remapped compactly so the remote card only sees the experts it actually holds.
6. eager execution gates Get correct tokens out before touching CUDA graphs, because graph capture hides bugs and changes failure modes.
7. in process C ABI plus a real device gate Collapse the cross process ring into an in process C ABI to remove a whole copy and a whole scheduling boundary, then re-qualify on real silicon.

why we had to write our own kernels

Then the checkpoint format changed. The model we wanted to serve ships in NVFP4, a 4-bit floating point format, and Intel's kernels do not read it. They handle 16-bit floats, 8-bit floats, and integers. Nothing that speaks NVFP4 existed for these cards anywhere.

Three options: convert the checkpoint to a format Intel's kernels could read, which we later measured as destroying quality; keep weights in 16-bit, which does not fit in memory and doubles the bytes crossing the link; or write the kernels. We wrote the kernels, and commit 1da05c3a is where Intel's come out and ours go in. Everything since is ours: the expert bank format, the grouped prefill kernel, the decode kernel, the placement policy, the doorbell.

Worth noticing what did not have to change when the math changed. The provider boundary, the ring layout, the placement policy and the plugin all survived, because the boundary was drawn around "give me routed expert work, hand back partial results" rather than around any particular kernel. Replacing a third of the system took one commit.

problems we ran into

None of these were in the plan. Each cost real time and each is now a line in the ledger.

  • the checkpoint lied about its own layout. The model declared one architecture but named its tensors like another, and its list of layers to leave unquantised carried the wrong prefix on 348 of 349 entries. Result: every 16-bit module got built as though it were quantised and rejected its own weights. Fixed with a prefix rewrite in our loader, which is a no-op for correct checkpoints.
  • a vendor kernel library that hangs the GPU. One MoE autotuner ran 25 minutes at full utilisation without finishing on this class of card. Skipping those ops reached a fallback that faulted on a misaligned address instead. We pinned the backend to a path that works and wrote down both failure modes.
  • a latent bug of ours, exposed by a stricter consumer. Our route remapping widened expert ids to 64-bit. Two previous kernels tolerated it; a third type-checked and threw. Fixed at the source rather than at the call site.
  • 47 GiB of host memory vanishing. Traced by instrumenting the boot: Intel's driver keeps a full host copy of everything on the card. Not a leak, not fixable by any flag we tried, and it killed an entire category of optimisation. Better to know.
  • prompt caching silently doing nothing. Measured 1.007× on a repeated prompt where it should have been enormous. The model mixes two attention types and the framework cannot cache the state of one of them, so caching was disabled by architecture, not by configuration. On the model we serve today it works, and measures about 139×.
  • a parity check that was itself broken. A parity check compared two runs that had generated different random inputs, and we spent an afternoon bisecting kernels for a bug that did not exist. The gate is now seeded. That one is in the ledger as a rule: an instrument has to be deterministic before it is allowed to accuse anything.
Act II  ·  the problem, properly

the weights do not fit on any single card

The model we serve is a mixture of experts, roughly 118 billion parameters. Squeezed into 4-bit it is still 58.2 GiB of weights. Every card in this machine holds 32 GB. The arithmetic is not subtle.

The normal answer is to buy one card big enough, a 96 GB datacenter part, and be done. That answer works. It is also wasteful, for two reasons that have nothing to do with price.

most of the model is unused on any given token

Mixture of experts means each layer holds 218 separate expert networks, and a token uses 10 of them. The other 208 sit there doing nothing for that token. So when you buy 96 GB of fast memory, you are buying it to store weights, not to compute with them. The storage requirement is huge, the compute requirement per token is small.

the intuition

It is a library, not a factory. You need shelf space for two hundred books because any one of them might be needed, but each reader only ever pulls ten. Paying for a reading room the size of the shelves is the mistake.

attention and experts need opposite things

Inside every layer there are two very different jobs, and they have opposite needs.

the jobhow often it touches memorywhat it needs
attention
plus the KV cache		 re-reads the entire cache for every token, so the traffic grows as the conversation grows closeness. It must sit next to the compute, on the fastest memory available. Latency here is paid on every token.
the experts read once per token, then not touched again until that expert is picked again capacity. They are enormous and rarely touched, so being a bit far away costs almost nothing.

When you buy one big card you are buying one kind of memory to satisfy both. Shooting Brake gives each job the hardware it actually wants: attention gets the closest, fastest memory on the fastest link, and the experts get cheap capacity a little further away.

a third problem, specific to this hardware

Splitting like this creates a problem the big card does not have. Every layer, twice, data has to cross the gap between the cards. On this machine that gap is PCIe, and it is the narrowest thing in the system by a wide margin.

Act III  ·  the architecture, in full

the main idea

You cannot move the experts. A single layer's worth of expert weights is about 430 MB, and there are 47 layers. Pushing that across a 6.44 GB/s link every token would take minutes per word. So the experts do not move. They are loaded into Arc memory once at startup and they stay there for the life of the server.

What moves is the tokens, and tokens are tiny.

Notice what is missing: there is no direct card to card link. The two Arcs cannot talk to the 5090 and the 5090 cannot talk to them. Everything goes through host memory. That is not a shortcut, it is the only road that exists.

the router: choosing 10 out of 218

Every layer, for every token, a small network scores all 218 experts and picks the best 10, with a weight for each saying how much that expert's opinion counts. Then those 10 get sorted by who owns them: about 1 lives on the 5090 and runs locally, and the remaining 9 split roughly 5 and 5 across the two Arc cards.

The experts themselves never move, so what gets sent to each card is small: the token's hidden state (3,072 numbers), the list of which experts to use, and their weights. The card looks up those experts in its own memory, does the math, and sends back a partial answer. The 5090 adds up all the partial answers and that is the layer done.

something we had to check

If routing were lopsided, one card would be swamped while the other idled. So we measured it on real prose. All 205 usable experts get picked, the ten most popular take only 7.2% of the traffic between them, and the busiest expert is only 1.63× the average. On natural text the split across the two cards came out 51.87% to 48.13%, which is about as even as you could ask for.

That mattered more than we expected. We nearly built a clever uneven split to compensate for a lopsidedness that only showed up with random synthetic prompts. On real text the even split is already near optimal, and tuning for the synthetic case would have made real text 6.4% worse. We caught it by testing on actual prose instead of generated tokens.

pinned memory and DMA

Two pieces of vocabulary, because everything after this depends on them.

what DMA is

A GPU does not politely ask the CPU to hand it data. It has its own engine that reaches into system memory and takes it, called direct memory access. The CPU is not involved. It is the difference between asking a colleague to fetch a file and having a key to the filing cabinet yourself.

what pinning is, and why it is required

Normally the operating system is free to shuffle your memory around: move a page somewhere else, swap it to disk, whatever it likes. That is fine for a CPU because the OS updates the address as it goes. It is fatal for a GPU, which has been handed a raw physical address and will happily read whatever is now sitting there.

Pinning (or page locking) tells the OS: this memory does not move, ever. Once a page is pinned, a GPU's DMA engine can read and write it at any moment without warning anyone. All our ring buffers are pinned for exactly this reason.

the intuition

Pinning is nailing the mailbox to the wall. Both parties can drop things in it and pick things up whenever they like, without checking whether someone moved the mailbox.

how the two combine

Pinned host memory is the one place both vendors' hardware can reach. NVIDIA's DMA engine can write it. Intel's DMA engine can read it. Neither needs to know the other exists. Two runtimes that share no API at all share a mailbox, and that is enough to build a handshake on.

the doorbell

This is the part with no equivalent in any shipping framework, so it gets the space.

The problem, plainly: 47 times per token, the 5090 has to stop and wait for two Intel cards to finish, then continue. CUDA has a rich set of tools for waiting on other CUDA work. It has nothing at all for waiting on an Intel GPU. Intel's runtime is the same in reverse. There is no shared clock, no shared event, no shared queue.

So we built a synchronisation primitive out of ordinary memory. Two 4-byte words in a pinned host page, per layer. One is the signal. One is the completion. That is the entire protocol.

what it costs

Today that handshake costs 61 microseconds per layer. Times 47 layers, that is about 2.9 milliseconds of every token spent just knocking on doors. On an 11.4 ms token, that is a quarter of the time.

So we went looking for something faster, and we found it.

the semaphore, and where it stopped

Intel's GPUs have a piece of hardware most people never think about, called the command streamer. It is the front end that reads the list of things the GPU has been told to do. And it can do something useful: it can be told wait until this memory location holds this value, and it will sit there checking, in hardware, with no CPU involved at all. The instruction is MI_SEMAPHORE_WAIT, exposed through an Intel extension.

That is exactly what we need. If the Arc card can wait on a memory word directly, we do not need a CPU core spinning, and we do not need the host in the loop at all. We measured it: 4.7 to 5.6 microseconds for the round trip, against 61 for the poller. Twelve times faster.

why the first version did not work

The obvious way to wire it up is to let Intel own the shared page and have CUDA write into it. So we asked CUDA to take an Intel allocated host page and register it for DMA, using cudaHostRegister. It refused. Error 1, invalid value, every time. Intel's host memory is backed in a way CUDA will not accept, and no flag combination changed that. We tried the driver debug keys too. All of them.

Worse, the failure mode is nasty. When you hand a raw unregistered host pointer to the Intel side, the driver does not fail loudly, it quietly falls back to copying the page into an internal buffer. Then the Arc waits on the copy forever while CUDA writes the original. It would look like a hang with no error anywhere. We found that trap in a probe, which is the only reason it never cost us a debugging week.

inverting the design

If CUDA will not accept Intel's memory, let CUDA own the memory instead and have Intel's command streamer wait on it. CUDA allocates the pinned page. Intel's hardware waits on a word inside it. We tested it on real silicon, both cards, 2,100 iterations:

And then it did not ship. Wiring the proven transport into the live engine wedged during CUDA graph capture, four separate times, in three different designs. The transport is proven. The integration is blocked on a driver level race we have isolated but not fixed. The number above is a projection and stays one until it serves a real token. We are not going to pretend otherwise.

one token, start to finish

Putting it together. This is what happens between you pressing enter and one word appearing.

why prefill and decode behave differently

Reading your prompt and writing the answer are the same math, but they land on the hardware completely differently, and once you see why, every result in this document makes sense.

reading your prompt, "prefill"

2,048 tokens go through together. An expert gets loaded from Arc memory once and then used for hundreds of tokens. The cost of fetching it is spread across all of them.

The cards are doing real, dense matrix work. This is the regime where engineering pays, and it did: 1,705 down to 387 microseconds per token, 4.40×.

writing the answer, "decode"

One token goes through alone. The same expert gets loaded, used once, and thrown away. Nothing is spread across anything.

And the 47 round trips are strictly sequential, so their latency cannot be hidden. Layer 12's input does not exist until layer 11 finishes.

the intuition

Prefill is a delivery van doing one round with two thousand parcels. Decode is the same van doing the same round with one parcel. The van costs the same either way. That is the whole story, and it is why the two halves of this system behave like different machines.

Act IV  ·  the numbers

our kernels compared to the alternatives

Every matrix kernel in this system is written by us. That was not a preference, it was forced: the checkpoint ships in NVFP4, a 4-bit floating point format, and Intel's matrix engines do not speak it. They handle 8-bit integers, 4-bit integers, and 16-bit floats. Nothing else. So somebody had to write the code that unpacks 4-bit weights and feeds them to hardware that has never heard of them, and no vendor had done it.

But we did not want to be precious about it. If someone else's kernel is faster, we should use theirs. So we benchmarked every credible alternative on this exact card, at our exact shapes.

two results we did not expect

First, we already beat Intel's own reference at our shapes. Their sycl-tla example hits 73 to 84 TFLOP/s in their benchmark, which looks like it should demolish our 20.5. But their number needs about 244 rows of work per expert to reach it. Real routing gives us about 30. At 30 rows their kernel drops to 13 or 14 TFLOP/s, and 3.58 ms per layer, against our 2.355. We are faster on their silicon, at the shape that actually occurs. The 3.3× gap we were worried about was an artefact of comparing at different fills.

why 4-bit wins here, in one line

A 16-bit kernel has to read twice the bytes of a 4-bit one. On a memory bound job, that sets a floor no amount of clever scheduling gets under. Two of the four candidates died on that arithmetic alone, before anyone looked at their code quality.

Second, the two fast candidates did not survive integration. Both looked 2.3 to 2.4× faster in isolation. Wired into the real engine the win came out roughly a wash, because the expert GEMM is not the only thing happening in a prefill step. They are parked behind a flag, ours stays the default, and the honest conclusion is that a microbenchmark win is a hypothesis, not a result.

This is the part we would want a reviewer to check hardest. We went looking for a reason to throw our own kernel away, found two candidates that beat it on the bench, integrated both, and kept ours because the end to end number said so.

Act V  ·  what we do not have yet

PCIe lanes

This is the biggest single lever in the system and it is not a chip, it is a slot.

Transfer is about 175 of the 387 microseconds of every token of prompt, roughly 45%. Give each Arc its own Gen5 ×16 root port and that link goes from 6.44 GB/s shared to something near 50 GB/s each, which is eight times more, and it stops being shared at all.

effect on our own numbers

First, that transfer time is mostly not hidden today. We already overlap transfer with compute, and it only gained 5 to 6%. If the transfer were already hidden behind the expert math, overlapping would have gained nothing at all. It gained a little, which means most of those 175 microseconds are still on the critical path.

Here is what each change does, measured against our own current numbers rather than against another card.

Each change on its own is worth about 1.5× on prompt processing. Together they are worth 2.4×, because they multiply rather than add. That is what happens when a job has two comparable costs sitting in series.

Why both are needed. Cut the link 8× and transfer drops to about 22 microseconds, small enough to hide completely behind the expert math. But then the expert math is the entire cost, so that is where you stop. Speed the expert math up 2.3× instead and it stops being the biggest term, so the transfer you did not fix becomes the new ceiling. Either one on its own leaves the other as the limit.

comparison against their card

Their curve bends upward because attention cost grows with the square of the prompt. Ours is close to a straight line because we are limited by a link and a link does not care how long the prompt is. So the question is not whether the lines converge, it is where.

four effects not in the table

  • the two cards stop fighting each other. Right now they share one uplink and lose about 34% to contention when both transfer at once. Separate root ports means separate budgets, and both cards run at full speed simultaneously.
  • bigger chunks become worth sending. More bandwidth means we can push more tokens per dispatch, which means more rows of work per expert, which is exactly the thing that makes the matrix engines efficient. This compounds with the faster kernel rather than just adding to it.
  • overlap starts actually working. We already overlap transfer with compute, and it buys 5 to 6%. That is small because the transfer is so much bigger than the compute window it hides behind. Shrink the transfer and the overlap covers all of it.
  • the doorbell round trip shortens. The handshake is a small write and a small read across the same link. Lower latency lanes make the 8 to 9 microsecond hardware handshake we already proved land at the fast end of its range.

what if the Arc cards were infinitely fast

This is worth asking directly, because the intuitive answer is wrong. If you handed us an Arc card with unlimited memory bandwidth, prompt processing would improve by almost nothing and generation would improve by about a quarter. Then it would stop. Here is why.

A prompt token costs 387 microseconds today. Taken apart, that is 175 microseconds of moving weights across PCIe, 187 microseconds of the Arc cards doing arithmetic, and 68 microseconds of routing, scheduling and host work. Those first two run partly at the same time, which is where the shipped number comes from.

A generated token costs 11.4 milliseconds. That splits very differently: 21.6% is the Arc cards actually working, 69.7% is the 5090 sitting idle between layers waiting for its own next launch, and the remaining couple of milliseconds is sampling and API overhead.

So a token's time sits in a few separate places. What follows removes one place at a time and reports what is left. A row reads "unchanged" when that cost is not part of that operation to begin with.

The 5090's waiting does not matter for prompts because a prompt processes 2,048 tokens per launch, so the launch cost is divided across all of them. Generation pays it 47 times for one token.

why an infinitely fast Arc card barely helps the prompt

Our prompt kernel reads about 430 MB of expert weights per layer. At the 603.5 GB/s we measured on the card, fetching that much should take 0.71 ms. We measure 2.355 ms. So the kernel is running at roughly 30% of the memory bandwidth it already has, and the other 70% of its time goes to unpacking 4-bit weights and doing the multiply.

Giving it more bandwidth does not help something that is not waiting on bandwidth. That is the whole argument for spending effort on a better kernel instead: the faster 4-bit kernel we benchmarked is 2.3× quicker on the same card at the same bandwidth.

why it does help generation, but only to a point

Generation is the opposite case. There the card reads one expert's weights to serve a single token, so there is no arithmetic to hide behind, and our kernel runs at 545 GB/s, about 90% of the card's ceiling. That one is genuinely bandwidth-limited and close to physics.

But it is only 21.6% of a generated token. Take Arc service to zero and 11.4 ms becomes about 8.9 ms, and there it stops, because the 5090 is still spending 7.9 milliseconds waiting between its 47 layers. That waiting is software, not silicon. No card fixes it.

The useful conclusion. Of the three things you could make infinitely fast, the Arc cards' own bandwidth is the least valuable. The link between the cards is worth 1.5× on prompts. Fixing our own per-layer overhead is worth 3.3× on generation. The card itself is worth 1.2× and 1.3×. We are not short of memory bandwidth. We are short of a good kernel on one side and disciplined scheduling on the other, and both of those are ours to fix.

One last number for scale. If all three were free and only the fixed 68 microseconds of routing and host work remained, a 32K prompt would take about 2.2 seconds. The 96 GB card we keep comparing against does that same prompt in 2.336 seconds today. So a perfect version of this design lands roughly level with their card, not far past it. The reason to build it is that it runs a model none of those cards can hold, at a fraction of the cost, not that the ceiling is higher.

memory capacity

The obvious guess is that faster host memory would help. It would not, and the reason is worth knowing: even a single channel of DDR5 is five to ten times faster than the PCIe link it feeds. Host memory bandwidth is nowhere near being our problem.

Space is. And for a reason nobody would predict: Intel's driver keeps a full copy in host memory of everything we put on the Arc cards. Byte for byte. 24.34 GiB per card, 47.4 GiB of the machine's 59.4, gone. That leaves 2.78 GiB free while serving, and the machine swaps.

We did not guess this, we instrumented the boot and watched it happen in two steps as each card loaded. Then we tried every driver flag that looked relevant. None of them changed it.

At 96 GB the same copy leaves about 45 GiB free instead of 2.78, which un-kills three things we had to abandon:

  • a third Arc card, because each one costs 24 GiB of host shadow and we simply do not have it. A third card means 57 experts per card instead of 85, so a third less work each.
  • keeping a copy of the experts in host memory for prefill, which we measured as needing 44 to 56 GiB and therefore impossible today.
  • no more swapping during long context serving, which currently costs us unpredictable stalls.

reusing cached prompts

Right now, when you come back tomorrow, your conversation is gone. The processed form of it, the part that took 59 seconds to compute at 127K tokens, lived in GPU memory and was evicted the moment something else needed the space.

That is silly, and it is fixable. The processed form of a conversation is just data. It can be written to host memory when the GPU needs the space, and to disk when host memory needs the space, and read back when you return. Then a returning user does not pay for their history again. They pay only for what they just typed.

why this is the most valuable unbuilt thing on this page

We already measured what happens when a prompt is already processed: about 139× faster. That is not a projection, that is the reuse we get today, within a session, while the data survives in memory. Everything above is about making that survive longer: an hour, a day, a week. The gap we lose to a datacenter card is entirely in first processing of a prompt. Making first processing rare is worth more than making it faster.

not built yet  This is a roadmap item, not a claim. The measured 139× is real; the persistence layer around it is designed and unwritten.

using the SSD as another memory tier

There is a natural hierarchy here, and we currently use only the top two floors of it.

The technique is called GPU direct storage: the SSD writes straight into GPU memory over PCIe, with no bounce through host memory and no kernel driver in the path. We have a library for it sitting in our vendor tree, uGDS, which builds the NVMe commands in user space and lets the drive DMA directly to the card.

Their published figures are 5.3× the bandwidth and 108× lower latency on small reads, 5.2 microseconds against 561, compared to NVIDIA's own GPU direct storage. Those are their numbers, not ours; we have not run it yet.

What it would be for: the conversation storage above. If a returning user's processed history can be pulled off an SSD straight into GPU memory in microseconds rather than milliseconds, then persisting conversations to disk stops being a fallback and becomes the normal path. It also makes the host memory shadow problem less painful, because cold data does not need to sit in host RAM waiting to be needed.

unexplored  Vendored, not tested. On the list, behind the things that are already measured.

the part no hardware fixes

Of the 11.4 ms it takes to produce a word, 7.9 ms is the 5090 orchestrating: hundreds of small kernel launches, graph replay overhead, and 47 doorbell handshakes. No PCIe generation touches that. No amount of memory touches it. It is software.

Three things attack it, and we know the size of each:

Which is why the drafter is the next thing we do, and why it is not a kernel problem.

current state

A 118 billion parameter model, in its native 4-bit format, is serving right now on one gaming GPU and two workstation cards, none of which holds even a third of it. It runs 131,072 tokens of context. Prompt processing is 4.40× faster than where this started. Generation speed matches a 96 GB datacenter card once the conversation gets long. Repeated prompts come back about 139× faster.

# Shooting Brake Risk Register

## Purpose and status

This register applies to the production direction in [`../plan.md`](../plan.md): upstream vLLM 0.26+ on one RTX 5090 as the CUDA state owner, plus one isolated persistent QuixiCore-XPU B70 routed-expert provider connected through a versioned pinned-memory request ring and a Qwen-scoped out-of-tree post-top-k adapter.

Colibri has proven important transport, placement, numerical, and failure-recovery mechanics. Phase 3 now adds direct physical-B70 evidence for the independent primary-NVFP4 artifact/source and provider-wire gate. It closes only the tested provider-side slice of R10 and narrows the provider-side portions of R4, R5, R8, R9, and R13; CUDA scatter/join, adapter parity, recovery execution, production placement, performance, and end-to-end acceptance remain open. Unless a row explicitly says otherwise, every remaining Phase 0–10 risk stays **open** until its production gate is recorded.

Risk responses follow three rules:

1. Correctness failures are never accepted as performance tradeoffs.
2. A model/provider combination that fails capability negotiation remains on stock vLLM CUDA; it is never sent through a generic or guessed B70 path.
3. CPU matrix execution is exact emergency recovery only. If it becomes normal-path work, the production design has failed its operating contract.

## Evidence already available, and its limit

The Colibri Qwen3.6 implementation provides reference evidence for:

- persistent B70 expert residency and compact layer/expert ownership;
- host-staged activation/metadata/weighted-partial transport;
- asynchronous single-token issue/take;
- Colibri-only signed-S4 GS64 conversion and ESIMD execution;
- numerical agreement with the Colibri CPU reference;
- exact failed-route recomputation;
- end-to-end CUDA+B70 generation with zero normal-path CPU expert fallback in the recorded suite.

Phase 1 adds direct evidence for explicit B70 selection, exact full-bank startup validation, fixed provider buffers, split/fused batched execution through `M=128`, duplicate top-8 weighting, generation/sequence rejection, allocation stability, and shutdown. Phase 2 adds a separately mapped CUDA/Level-Zero pinned-memory probe, the protocol-v2 eight-slot process ring, deterministic lifecycle/failure stress through 2,000,000-request wraparound, process-isolated real-B70 numerical execution, exact dispatch/allocation accounting, and warmed stage percentiles. Phase 3 adds a frozen independent BF16-source/NVFP4 oracle with authenticated bank, shard manifest, and fixture; sampled byte-level artifact audit; a physical-B70 `M=1..128` process-ring numerical matrix; compact canonical remap; zero-remote no-publication; mixed-route invariance; trusted bootstrap/unsupported-shape negatives; and split/fused sequence-bound failure publication. These results close the direct provider-wire slice for the pinned primary NVFP4 bundle. They do **not** close upstream-vLLM integration, CUDA scatter/join, full dual-artifact or layer/logit/generation parity, production placement, concurrency/throughput, exact recovery execution, or production acceptance.

## Stop and fallback rules

1. Any selected-route correctness mismatch, stale completion, ownership overlap/hole, or silently incomplete output stops hybrid qualification.
2. Any format or capability mismatch fails at startup; it is not repaired with an undocumented generic kernel.
3. A provider failure either triggers exact route recovery or fails the request explicitly.
4. If B70 cannot provide capacity or performance benefit after full production accounting, the affected model/configuration remains on stock all-CUDA vLLM; Colibri reference success is not grounds to force deployment.
5. If provider-wrapper overhead alone is material, the framework-neutral QuixiCore-XPU C++ ABI may replace the wrapper behind the same protocol. This does not justify changing the CUDA host, router semantics, or failure contract.
6. Thresholds for numerical tolerance, timeout, recovery rate, graph noise, and performance acceptance must be declared before the corresponding gate is run.
